# Qdot AX Assignment

브랜드몰의 상품 정보를 수집하고 AI로 분석해 큐닷 파트너 상품 등록 스키마인 `PartnerProductCreateInput`으로 정규화하는 도구입니다.

## 1. 프로젝트 개요

이 프로젝트는 다음 파이프라인을 구현합니다.

```text
브랜드몰 URL
  -> 스토어 유형 탐지 및 상품 크롤링
  -> 상품별 최저가 탐색과 AI 분석 병렬 실행
  -> Zod 스키마 검증
  -> SSE 진행 상황 및 정규화 결과 제공
```

핵심 기능:

- 등록 스토어 전체 또는 개별 크롤링
- 사용자가 입력한 임의 쇼핑몰 URL 크롤링
- 수집 개수와 AI 분석 진행 상황 실시간 표시
- 상품명, 이미지, 가격, 옵션 등 원천 데이터 수집
- 품절 상품·품절 옵션 값 자동 제외
- OpenAI를 이용한 해시태그, USP, 카테고리 분석
- `PartnerProductCreateInput` 스키마 검증 및 JSON 다운로드

> 최저가 탐색 기능(네이버쇼핑·쿠팡 검색 결과 기반)은 구현되어 있으나, 검색 결과 차단과 동명이품 매칭 위험으로 현재 파이프라인에서는 비활성화되어 있습니다. 따라서 `lowest_price` 관련 필드는 항상 `null`로 출력됩니다.

### 대상 스토어

| 구분                | URL                                       | 현재 상태                                                          |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------------ |
| 네이버 브랜드스토어 | <https://brand.naver.com/kefii>           | 활성화                                                             |
| 네이버 스마트스토어 | <https://smartstore.naver.com/phytonutri> | 크롤러 구현 완료, 실행 환경의 접근 제한으로 기본 목록에서 비활성화 |
| 브랜드 공식몰       | <https://m.happylandmall.com/>            | 활성화                                                             |

### 지원 어댑터

`crawlUniversal`은 최초 HTML과 URL을 점수로 평가해(`selectAdapter`) 가장 높은 점수의 전용 어댑터를 선택하고, 어느 어댑터도 점수를 얻지 못하면 범용 어댑터로 폴백합니다. 단일 `detect()` 통과 여부 대신 호스트명·경로·HTML 시그널마다 가중치를 더하는 방식이라, 같은 솔루션을 쓰는 다양한 스킨에도 더 안정적으로 매칭됩니다.

| 어댑터            | 처리 방식                                                  |
| ----------------- | ---------------------------------------------------------- |
| Naver Brand Store | Playwright와 내부 응답 데이터 활용                         |
| Naver Smart Store | Playwright 우선, axios API 요청 fallback                   |
| Godomall          | 카테고리·목록·상세 HTML 파싱                               |
| Firstmall         | `goodsInfo` 메타데이터와 카테고리 페이지 파싱              |
| Cafe24            | Cafe24 마크업 탐지, 카테고리·상세 옵션 파싱                |
| Nuxt              | Nuxt(`__NUXT__`) 기반 SPA의 API·렌더링 응답 캡처           |
| WordPress         | WooCommerce Store/REST API와 상품 목록 HTML 파싱           |
| Generic           | 공통 API·CSS 패턴·LLM 셀렉터 탐지·Playwright 순차 fallback |

Cafe24의 Turnstile 접근 제한 페이지는 Cafe24 쇼핑몰로 탐지하되 CAPTCHA를 우회하지 않고 명확한 오류를 반환합니다.

## 2. 실행 방법

### 요구 환경

- Node.js 20 이상
- npm
- Chromium 실행이 가능한 환경
- OpenAI API Key

### 환경 변수

프로젝트 루트에 `.env.local`을 생성합니다.

```env
OPENAI_API_KEY=your_openai_api_key_here
```

### 설치 및 실행

```bash
npm install
npx playwright install chromium
npm run dev
```

브라우저에서 <http://localhost:3000>에 접속합니다.

프로덕션 빌드 확인:

```bash
npm run build
npm start
```

### API

두 엔드포인트 모두 `text/event-stream`으로 진행 상황과 결과를 반환합니다.

| 메서드 | 경로                                   | 설명                                     |
| ------ | -------------------------------------- | ---------------------------------------- |
| `GET`  | `/api/crawl?store=all`                 | 등록 스토어 크롤링                       |
| `GET`  | `/api/crawl?store=naver-brand&limit=5` | 특정 등록 스토어 상품 수를 제한해 크롤링 |
| `POST` | `/api/crawl`                           | 요청 본문의 단일 URL 크롤링              |

단일 URL 요청 예시:

```bash
curl -N -X POST http://localhost:3000/api/crawl \
  -H "Content-Type: application/json" \
  -d '{"url":"https://brand.naver.com/kefii"}'
```

주요 SSE 이벤트:

```text
progress(crawl) -> crawl_done -> analyze_start -> progress(analyze) -> done
```

`crawl_done`은 크롤링이 끝난 시점의 수집 총계(`total`)와 분석 대상 수(`limited_total`)를 전달하며, UI는 이를 이용해 수집 개수와 분석 진행률을 표시합니다.

## 4. 회고

### 문제를 정의한 방식

처음에는 세 대상 스토어만 처리하면 됐지만, 실제 브랜드몰은 같은 상품 정보라도 노출 구조가 달랐습니다. 그래서 문제를 단순한 CSS 셀렉터 작성이 아니라 다음 세 단계로 나눴습니다.

1. 쇼핑몰 솔루션 또는 사이트 유형 탐지
2. 상품 원천 데이터 수집
3. AI 분석과 스키마 검증을 통한 정규화

### 고민한 지점

가장 많이 고민한 부분은 옵션 수집과 범용성입니다. 옵션은 목록에 없고 상세 페이지에만 있거나, 스펙 표·셀렉트 박스·라디오 버튼처럼 서로 다른 형태로 노출됩니다. 그래서 크롤러가 가능한 옵션 문자열을 먼저 수집하고 AI가 `option1`, `option2` 축으로 분류한 뒤 라벨 접두사를 정규식으로 제거하도록 구성했습니다.

범용 크롤러는 공통 API와 알려진 HTML 패턴을 먼저 시도하고 실패하면 LLM으로 반복 상품 카드 셀렉터를 찾고 마지막으로 Playwright 렌더링 결과를 분석합니다. 빠른 경로부터 비용이 큰 경로까지 단계적으로 실행합니다.

### 트레이드오프

- Playwright는 동적 사이트 처리에 유리하지만 실행 시간이 길고 메모리 사용량이 큽니다. 정적 HTML 처리가 가능한 어댑터는 axios와 Cheerio를 우선 썼습니다.
- 상세 옵션을 많이 수집할수록 결과 품질은 좋아지지만 요청 수가 늘어납니다. 사이트별 동시성 제한을 두어 속도와 차단 위험 사이를 조정했습니다.
- LLM 기반 셀렉터 탐지는 커스텀 쇼핑몰 대응 범위를 넓히지만 항상 정확하지는 않고 API 비용이 발생합니다. 전용 어댑터와 정적 패턴이 모두 실패한 경우에만 사용합니다.
- 최저가 검색은 별도 제휴 API 없이 공개 검색 결과를 이용하므로 차단, 검색 결과 변경, 동명이품 매칭 위험이 있습니다. 토큰 유사도와 비정상 가격 필터를 적용했지만 신뢰도가 충분치 않았습니다. 잘못된 가격을 결과에 섞기보다 현재는 파이프라인에서 비활성화하고 `lowest_price` 관련 필드를 `null`로 두는 쪽을 택했습니다. 구현 자체는 `lowest-price.ts`에 남겨 두었습니다.

### 해결하지 못한 것과 이유

- 네이버 스마트스토어는 크롤러를 구현했지만 실행 환경에 따라 로그인 또는 `429` 차단이 발생합니다.
- 일부 Cafe24 쇼핑몰은 Cloudflare Turnstile 기반 접근 제한을 반환합니다. CAPTCHA 자동 우회는 구현하지 않았습니다. 해당 페이지를 Cafe24로 탐지한 뒤 접근 제한 오류를 반환합니다.
- 범용 어댑터는 모든 커스텀 스킨을 보장하지 않습니다. 상품 정보가 비공개 API, 로그인 세션, 복잡한 클라이언트 상태에만 존재하면 수집하지 못할 수 있습니다.
- 자동화 테스트 환경은 구성하지 못했습니다. 현재 검증은 프로덕션 빌드, 로컬 모사 HTML, 실제 사이트 실행을 중심으로 했습니다.

### 새로 알게 된 점

- 같은 쇼핑몰 솔루션을 쓰더라도 스킨과 접근 제한 설정에 따라 HTML과 크롤링 가능 여부가 크게 달라집니다.
- 크롤러 정확도뿐 아니라 차단 대응, 진행 상황 표시, 실패 원인 전달도 사용자 경험에서 중요한 부분이었습니다.
- 품절 같은 상태 신호는 파싱 시점에만 온전히 남습니다. `disabled` 속성이나 `soldout` 클래스 같은 구조 신호는 옵션을 `"라벨: 값"` 문자열로 평탄화하는 순간 사라지므로, 어떤 단위로 거를지는 추출 시점에 결정해야 했습니다.
- 어댑터 선택은 단일 `detect()` 참/거짓보다 여러 신호를 가중 합산하는 점수 방식이 훨씬 견고했습니다. 같은 솔루션의 스킨 변형이나 접근 제한 페이지처럼 한 조건만으로는 갈리지 않는 경우가 많았기 때문입니다.
- 빠른 경로부터 비싼 경로까지 단계적으로 시도하는 구조(정적 HTML·공개 API → LLM 셀렉터 탐지 → Playwright 렌더링)가 정확도와 비용·속도를 동시에 잡는 현실적인 타협점이었습니다.
- 동시성 제한(`p-limit`)은 속도 조절 수단이자 차단 회피 수단이기도 했습니다. 요청을 빠르게 몰아치면 오히려 사이트 차단으로 전체가 느려졌습니다.

### 더 시간이 있었다면

- 어댑터별 HTML fixture와 파서 단위 테스트 추가
  - 실제 쇼핑몰에서 받아온 HTML을 샘플 파일로 저장해 두고 각 어댑터가 거기서 상품명·가격·옵션을 제대로 뽑는지 자동으로 검사하는 테스트입니다. 지금은 사이트에 직접 접속해 눈으로만 확인하기 때문에, 파싱 코드를 고치다 다른 부분이 깨져도 바로 알기 어렵습니다. 테스트가 있으면 네트워크 없이 빠르게 문제를 잡는 안전망이 생깁니다.

- 작업 큐, 재시도, rate limit, 캐시를 포함한 비동기 처리 구조 도입
  - 지금은 한 번의 요청 안에서 크롤링부터 AI 분석까지 한 번에 끝나기 때문에, 상품이 많으면 요청이 길어지고 중간에 실패하면 처음부터 다시 해야 합니다. 크롤링을 백그라운드 작업으로 분리하고(작업 큐), 일시적 실패는 자동으로 다시 시도하고(재시도), 사이트별 요청 속도를 조절해 차단을 줄이고(rate limit), 같은 페이지를 반복해서 받지 않도록 저장해 두면(캐시) 실제 서비스 수준의 안정성을 갖춥니다.

- 최저가 결과의 상품 동일성 검증 강화 및 제휴 가격비교 API 연동
  - 비활성화해 둔 최저가 기능의 핵심 문제는 "검색 결과가 정말 같은 상품인지" 판별하는 일입니다. 지금은 상품명이 비슷하면 같은 것으로 보기 때문에 이름만 닮은 다른 상품을 잘못 매칭할 수 있습니다. 브랜드·모델명·용량 같은 핵심 속성으로 더 엄격하게 대조하고 검색 결과를 긁는 대신 네이버 쇼핑검색 같은 정식 제휴 API를 쓰면 차단 걱정 없이 정확한 가격을 얻습니다.

## 6. 필드별 처리 설명

| 필드                        | 처리 주체                    | 처리 방식                                                                                                                                                  |
| --------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `brand_name`                | 크롤링/스토어 설정           | 등록 스토어는 설정값을 사용합니다. 직접 입력 URL은 `og:site_name`, 문서 제목, 호스트명 순서로 결정합니다.                                                  |
| `name`                      | 크롤링                       | 상품 목록 또는 상세 페이지에서 원문 상품명을 수집합니다.                                                                                                   |
| `image_url`                 | 크롤링 + 검증                | 대표 이미지 URL을 절대 URL로 변환하고, 유효하지 않으면 원본 또는 placeholder를 사용합니다.                                                                 |
| `option1`                   | 크롤링 + AI + 정규식         | 상세 페이지에서 옵션 후보를 수집하고 AI가 첫 번째 옵션 축으로 분류합니다. 라벨 접두사를 제거하며 값이 없으면 `null`입니다.                                 |
| `option2`                   | 크롤링 + AI + 정규식         | 두 번째 옵션 축을 같은 방식으로 처리하며 값이 없으면 `null`입니다.                                                                                         |
| `consumer_price`            | 크롤링                       | 정상가·소비자가를 숫자로 변환합니다. 별도 정상가가 없으면 판매가를 사용합니다.                                                                             |
| `sales_price`               | 크롤링                       | 현재 판매가 또는 할인판매가를 숫자로 변환합니다.                                                                                                           |
| `lowest_price`              | 최저가 크롤링(현재 비활성화) | 네이버쇼핑·쿠팡 검색 결과 중 상품명 토큰 유사도와 가격 필터를 통과한 최저 가격을 사용하도록 구현했으나, 신뢰도 문제로 현재 비활성화되어 항상 `null`입니다. |
| `lowest_price_source`       | 최저가 크롤링(현재 비활성화) | 선택된 최저가 후보의 플랫폼명을 저장하도록 구현했으나 현재 항상 `null`입니다.                                                                              |
| `lowest_price_collected_at` | 최저가 크롤링(현재 비활성화) | 최저가 후보 수집 시각을 ISO 8601 문자열로 저장하도록 구현했으나 현재 항상 `null`입니다.                                                                    |
| `discount_rate`             | 크롤링 + AI + 검증           | 원천 할인율이 있으면 사용하고, 없으면 정상가와 판매가로 계산합니다. 최종 값은 `0~100` 범위로 제한합니다.                                                   |
| `hashtags`                  | AI + fallback                | AI가 핵심 키워드 3~7개를 생성합니다. 유효한 결과가 없으면 상품명 토큰으로 보완합니다.                                                                      |
| `usp`                       | AI                           | 상품 정보와 옵션을 바탕으로 핵심 차별점을 한 문장으로 생성합니다.                                                                                          |
| `category_group`            | AI + Zod                     | AI가 허용된 카테고리 enum 중 하나 이상을 선택하고 Zod가 최종 검증합니다.                                                                                   |

정규화 이전 단계에서 품절 처리를 두 층위로 나눕니다. 상품명·설명·카테고리·URL에 품절·일시품절·sold out 패턴이 있으면 `filterSoldOutProducts`로 상품 전체를 제외합니다.
옵션의 경우 각 어댑터가 옵션 값을 수집할 때 품절 값만 제거하고(텍스트 접미사 + `disabled`·`soldout` class 등 구조 신호로 판정) 판매 가능한 값은 보존하며, 한 옵션 그룹의 값이 모두 품절이면 그 그룹을 드롭합니다. 판매 가능한 상품만 위 필드로 정규화됩니다.
